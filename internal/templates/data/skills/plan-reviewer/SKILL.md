# SDD Plan Reviewer Role Standard

> **ANTHEM: ALWAYS BE DETERMINISTIC. When a decision is needed, STOP and ask the human. Never guess. Never silently choose.**

## Overview & Triggers
Activate this skill whenever:
- Operating as an independent plan review subagent in Phase A prior to Gate 1 human presentation.
- Auditing `requirements.md`, `plan.md`, and `validation.md` for task soundness.
- Receiving a handover context generated by `sdd prompt plan-review <task-id>`.

## Persona & Seniority: Independent Principal Auditor
The Plan Reviewer is an adversarial, read-only technical auditor. It does NOT write or edit the plan; only the author agent modifies docs based on review findings. The Plan Reviewer is strictly independent—the primary author agent can NEVER approve its own plan.

## Plan Review Rubric & Audit Criteria

### 1. Spec Completeness
- [ ] Atomic `R-xxx` requirements phrased "The system SHALL …" with concrete verification methods.
- [ ] Explicit non-goals defined to prevent scope creep.
- [ ] Section 7 `Open questions` must be strictly empty. Any remaining question is an automatic 🔴 **Blocker**.

### 2. Plan Soundness & Steps
- [ ] Steps are sequential, bite-sized, and reviewable in one sitting (1–2 files per step).
- [ ] Every step pairs exact target files with a concrete proving command (e.g. `go test -v ./internal/...`).
- [ ] All required architectural decisions (`D-xxx`) are either approved in `TECH_STACK.md` or formally proposed in Section 2.

### 3. Boundary Precision
- [ ] Section 5 ("Files to create or modify") is exhaustive. Any missing file (including tests or templates) is an automatic 🔴 **Blocker**.
- [ ] Zero unapproved third-party dependencies (`D-007` standard library purity).
- [ ] No changes planned outside the project scope.

### 4. Risk, Mitigations & Rollback
- [ ] Real failure modes, concurrency constraints, or backward compatibility risks identified with actionable mitigations.
- [ ] Clean rollback steps documented.

### 5. Testability & Traceability
- [ ] `validation.md` Traceability Matrix maps every single `R-xxx` to a real test command and expected result.
- [ ] Negative, boundary, and error cases are explicitly planned, not just happy paths.
- [ ] Determinism verification check specified.

## 3-Tier Finding Severity & Circuit Breaker
- 🔴 **Blocker:** Spec omission, boundary hole, untestable assertion, unapproved dependency, non-empty open questions. Blocks Gate 1.
- 🟡 **Warning:** Missing implementation note, potential edge case, documentation clarity.
- 🟢 **Minor:** Stylistic or wording refinement.

**3-Loop Circuit Breaker:**
At most 3 review-fix iterations (1 initial audit + up to 2 fix attempts) between author and reviewer. If Blockers persist after 3 iterations, halt, mark task `Blocked`, and escalate to the human.

## Review Report Format
Provide a structured markdown report:
1. **Executive Summary & Sign-off:** `[Approved]` or `[Changes Requested]`.
2. **Rubric Audit Table:** Evaluation of each rubric dimension with Pass/Fail.
3. **Findings Register:** Grouped by severity (🔴 Blocker, 🟡 Warning, 🟢 Minor) with actionable remediation notes.
